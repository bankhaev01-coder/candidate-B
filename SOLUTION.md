# Решение: отчёт по выплатам и остаткам на дату

Консольная программа на Python: читает `contracts.csv`, `works.csv`,
`payments.csv` из каталога `data/`, восстанавливает состояние на отчётную дату
и считает по каждой работе «цена / выплачено / осталось оплатить», а по каждому
договору — итоги. Деньги считаются в `Decimal`, без `float`.

## Требования

- Python 3.11 или новее (проверено на 3.13.4, Windows).
- Сторонних библиотек нет: только стандартная библиотека
  (`csv`, `decimal`, `datetime`, `argparse`, `unittest`). `requirements.txt`
  поэтому пустой по существу.
- Кодировка файлов — UTF-8, разделитель в CSV — запятая.

## Запуск

Из каталога проекта:

```powershell
python main.py
```

Без параметров: данные из `data/`, отчётная дата 10.11.2026, отчёты пишутся в
текущий каталог. С параметрами:

```powershell
python main.py --data-dir data --as-of 10.11.2026
python main.py --data-dir data --as-of 2026-11-10 --out-dir out
python main.py --help
```

`--as-of` принимает `DD.MM.YYYY` и `YYYY-MM-DD`, дата включается в интервал.
Коды возврата: `0` — отчёт построен; `1` — ошибка данных или записи файлов
(сообщение с файлом, строкой и полем); `2` — неверные параметры командной
строки.

## Как устроен расчёт

1. Загрузчик проверяет файлы, колонки, типы, ссылки и хронологию. Фатальные
   проблемы останавливают работу с сообщением «файл, строка, поле»; мягкие
   расхождения попадают в список замечаний.
2. Работы и платежи переводятся в историческое состояние на отчётную дату по
   датам событий, а не по `status` (см. `DECISIONS.md`, п. 1).
3. Все оплаты и возвраты выстраиваются в один хронологический поток: сначала
   по дате, при равенстве — по номеру платежа, возврат всегда после оплаты.
4. Платёж с `work_id` или с однозначным номером/названием работы в назначении
   относится на работу целиком. Остальные распределяются пропорционально
   остаткам стоимости работ договора, с округлением до копейки методом
   наибольших остатков. Отменённые на дату платежа работы не участвуют.
5. Возврат снимает ровно те доли с тех работ, куда платёж был отнесён, и
   заново не распределяется.
6. По каждому договору считаются суммы и проверяется контроль:
   `выплачено (нетто) = распределено на активные + на отменённые +
   нераспределено`, а `остаток = стоимость активных работ − распределено на
   активные`. Если контроль не сходится, программа сообщает о внутренней
   ошибке и не выдаёт отчёт.

Подробное обоснование каждого правила с числами этой выгрузки — в
`DECISIONS.md`.

## Как проверялась правильность

- Показатели посчитаны вручную по исходным CSV и закреплены в тестах
  `tests/test_report.py`: `D-1` — 315 000.00 выплачено, 235 000.00 остаток;
  `D-2` — 75 000.00 и 15 000.00.
- На каждом договоре проверяются инварианты: распределённые суммы равны
  выплатам, остаток равен разнице стоимости активных работ и выплат по ним,
  сумма строк каждого платежа равна сумме платежа (или меньше ровно на
  нераспределённую часть).
- Повторный запуск даёт побайтово те же файлы: в отчётах нет даты генерации и
  случайных значений, сортировка естественная (`W-2` раньше `W-10`).
- Тесты на реальной выгрузке дополнены тестами на синтетических данных для
  сценариев, которых в выгрузке нет: переплата, возврат после отмены работы,
  неоднозначное назначение, платёж больше стоимости работ, платежи в один день.

## Ограничения и допущения

- Сумма возврата в данных не хранится, поэтому `refunded` трактуется как полный
  возврат платежа (`DECISIONS.md`, п. 5).
- У работ нет даты появления в выгрузке; считается, что они существуют с даты
  подписания договора (`DECISIONS.md`, п. 10).
- Валюта одна, НДС, курсы и удержания не моделируются — в данных их нет.
- Зачёт переплаты одной работы в счёт другой не выполняется автоматически:
  переплата и выплаты по отменённым работам показываются к согласованию.
- Отчёт не меняет исходные данные и не пишет в `data/`.
